# API Swagger 文档 Spec

## 背景

BinRag 已完成 API 层：16 条 RESTful 接口（知识库 5、文档 3、任务 2、问答 2、API Key 4），统一响应格式 `{code, message, data}`，全部接口经 `Authorization: Bearer <key>` 认证。但**没有任何接口文档**——外部调用方只能读代码或猜测请求/响应结构，对接成本高。

`docs/00-开发路线图.md` 阶段七明确列出「Swagger 文档」任务；`docs/06-api/决策记录.md` 记录「Swagger：本阶段不做，后续按需引入 swaggo」。本阶段补齐该承诺。

## 目标

- 为全部 RESTful 接口生成 OpenAPI 3 规范的机器可读文档
- 提供可交互的文档界面（Swagger UI），浏览器访问即可查看并测试接口
- 文档覆盖：接口路径/方法、请求参数、请求体结构、响应结构、认证方式

## 功能需求

- F1: 文档可访问——提供浏览器可访问的文档页面，展示全部 16 条接口（验证：浏览器打开文档 URL 可见接口列表）
- F2: 接口全覆盖——每条接口都有路径、方法、摘要、请求参数/请求体、响应结构描述（验证：逐接口核对文档与代码一致）
- F3: 认证说明——文档标注全部接口需要 `Authorization: Bearer <key>`，401 语义与错误响应结构明确（验证：文档含安全认证章节）
- F4: 统一响应文档化——文档说明成功/错误统一格式 `{code, message, data}` 及业务码含义（验证：文档含响应格式说明）
- F5: 可交互测试——文档页面支持输入 API Key 与参数发起真实请求（验证：在文档页面带 Key 调用列表接口成功）
- F6: 与实际行为一致——文档中的路径、方法、参数、响应字段与代码实现一致，无过时或错误项（验证：抽样接口比对文档与实测响应）

## 非功能需求

- N1: 零运行时影响——文档生成与注解不改变任何接口的请求/响应行为（验证：`go test ./...` 无回归）
- N2: 构建集成——文档生成产物纳入构建流程，`go build ./...` 后文档可用（验证：构建命令含 swag 生成步骤且通过）
- N3: 认证一致性——文档页面本身是否需要认证与后端配置一致（auth_enabled=false 时文档无需 Key 也可查看）

## 不做的事

- 不改动任何现有接口的路径、方法、参数或响应结构（仅添加文档注解）
- 不做接口版本化（v2）或废弃接口标记
- 不生成静态离线文档站（仅 Swagger UI 在线页面）
- 不覆盖认证中间件之外的鉴权细节（如多用户权限，本阶段无）

## 验收标准

- AC1: 浏览器访问文档 URL 返回 200 并渲染 Swagger UI（验证：GET 文档首页 200）
- AC2: 文档列出全部 16 条接口，路径与方法与 `router.go` 一致（验证：逐条比对）
- AC3: 每条接口文档含摘要、参数/请求体、响应结构，无占位符（验证：抽查各 handler 的注解完整性）
- AC4: 文档含 Bearer 认证说明，带 Key 可在文档页调用接口成功、错误 Key 返回 401（验证：文档页实操）
- AC5: 文档含统一响应格式说明（code/message/data 与业务码）（验证：文档内容检查）
- AC6: 注解不影响运行时行为——`go build ./...`、`go test ./...`、`go vet ./...` 全部通过（验证：命令执行）
- AC7: 生成文档产物与代码同步更新（验证：重新生成后 git diff 反映注解变更）
