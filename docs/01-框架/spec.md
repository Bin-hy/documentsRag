# 文档加载器 Spec

## 背景

BinRag 是一个 Go 语言实现的文档 RAG 系统。文档加载器是整个 Pipeline 的第一个环节，负责将多种格式的原始文档转换为统一的结构化中间表示，供后续分块器和 Embedding 模块消费。

## 目标

- 提供统一的文档加载抽象，支持 7 种常见文档格式
- 输入为 `io.Reader` + 文件元信息，输出为结构化文档对象
- 保留基础文档结构（标题层级、段落、列表）
- 错误处理可配置（宽容/严格两种模式）
- 职责边界清晰：只负责解析，不做分块

## 功能需求

- F1：格式支持 — 支持加载以下 7 种文档格式：TXT、Markdown、PDF、DOCX、CSV、Excel（xlsx）、HTML
- F2：统一输入接口 — 接收 `io.Reader` 和文件元信息（文件名、MIME 类型、文件大小），不关心数据来源
- F3：结构化输出 — 输出包含有序内容块的文档对象，每个内容块带有类型标记（标题/段落/列表项），标题块携带层级信息
- F4：元数据提取 — 从文件元信息和文档内容中提取元数据：文件名、格式、大小、标题（如有）、页数或段落数
- F5：格式自动识别 — 根据文件扩展名和 MIME 类型自动选择对应的解析器，无需调用方手动指定
- F6：错误处理可配置 — 提供严格模式（解析失败返回错误）和宽容模式（跳过损坏部分，记录警告，返回已解析内容），默认宽容模式
- F7：解析器可扩展 — 支持注册新的格式解析器，无需修改现有代码

## 非功能需求

- N1：内存效率 — 加载大文件时不将整个文件内容一次性加载到内存，PDF/DOCX 等二进制格式除外（受三方库限制）
- N2：并发安全 — 多个加载器实例可并发工作，无共享可变状态
- N3：可测试性 — 每种格式解析器可独立单元测试，输入为 `io.Reader`，不依赖文件系统
- N4：依赖可控 — 三方库选型优先选择维护活跃、Go 原生实现的库，避免 CGO 依赖
- N5：性能基线 — 单个 1MB 文本文件加载耗时不超过 100ms，10MB PDF 不超过 3s（非硬性指标，作为优化参考）

## 不做的事

- 不做文档分块（属于 Chunker 模块职责）
- 不做 Embedding 生成
- 不做文件上传/传输/存储（属于 API 层职责）
- 不做图片内容识别（图片跳过或仅保留 alt 文本）
- 不做 OCR（扫描版 PDF 不处理，仅支持文本型 PDF）
- 不做文档格式转换（不输出 HTML/Markdown，输出统一的中间结构）
- 不做国际化/多语言检测

## 验收标准

- AC1：分别传入 TXT、Markdown、PDF、DOCX、CSV、Excel、HTML 格式的测试文件，均能正确输出结构化文档对象
- AC2：传入 `io.Reader`（非文件路径），加载器正常工作
- AC3：Markdown 文件加载后，输出的内容块正确标记标题层级（h1/h2/h3）和段落类型
- AC4：传入损坏的 PDF，宽容模式下返回已解析内容 + 警告信息，严格模式下返回错误
- AC5：注册一个自定义格式解析器后，加载器能自动识别并使用它
- AC6：未知格式文件传入时，返回明确的「不支持的格式」错误
- AC7：单元测试覆盖全部 7 种格式，测试不依赖外部文件系统（使用 `bytes.Reader` 等内存数据源）
