# 策略可选化配置 决策记录

> 本文档记录阶段四（策略可选化配置）实现过程中的关键技术决策、理由与权衡。本阶段是 RAG 优化计划（docs/15-rag优化计划.md）的最后阶段，至此四阶段优化全部完成。

## 决策 1：策略统一封装为 StrategyConfig（六字段 JSON）

**选择：** 新增 `StrategyConfig`（query/fusion/decomposition/step_back/hyde/routing 六字段，string 枚举），贯穿 config.yaml、DB JSON 列、API 请求体、前端表单，全链路同构序列化。

**理由：**
- 字段级可选（omitempty）——知识库/请求只需设置想覆盖的项，其余继承
- 单结构多处复用（yaml/json tag 双标注），避免每层各自维护
- 与阶段一~三的散开关（`multi_query_enabled` 等）通过 `effective()` 兼容推导衔接

## 决策 2：三级覆盖（请求 > 知识库 > 全局），字段级继承

**选择：** `ResolveStrategy(global, kb, req)`——非空字段逐级覆盖，空字段继承低层级，最终默认值兜底（multi/rrf/off）。

**理由：** 用户确认的 spec 要求；字段级继承比整体覆盖更灵活（kb 只需设想改的项）；实现简单（`pick` 函数）。

**实测：** kb 设 `decomposition=parallel`，请求覆盖 `query=single/fusion=none` → 生效策略 = single/none/parallel（query/fusion 被请求覆盖，decomposition 继承 kb）——三级合并正确。

## 决策 3：旧开关兼容（effective 内推导）

**选择：** `effective()` 中，当 `cfg.Strategy` 全空时从旧开关（`MultiQueryOn()` 等）推导全局默认；否则用 `cfg.Strategy`。

**理由：** 阶段一~三的测试与现有部署依赖 `multi_query_enabled` 等旧字段；不破坏即兼容（N1）。生产 config 有 `rag.strategy` 段时走新结构，无则旧开关兜底。

**踩坑：** 旧开关推导时 `MultiQueryOn()=false` 必须显式设 `query=single + fusion=none`，否则 `ResolveStrategy` 默认 multi+rrf，且 `single+rrf` 触发非法组合校验 → effective 降级默认（曾导致测试失败，已修复）。

## 决策 4：校验集中到 ValidateStrategy（ResolveStrategy 内调用）

**选择：** `ValidateStrategy` 校验枚举合法性 + 3 种非法组合（single+rrf、routing=auto+decomposition≠off、routing=auto+step_back=on），`ResolveStrategy` 尾部调用，错误返回给调用方降级。

**理由：** 单一入口（配置加载、请求校验、kb 读取都经过它）；错误降级为全局默认而非拒绝请求（N2 校验时机 + 容错平衡）。

## 决策 5：knowledge_bases 加 strategy 列（ALTER 幂等迁移）

**选择：** `Migrate` 中追加 `ALTER TABLE knowledge_bases ADD COLUMN IF NOT EXISTS strategy TEXT NOT NULL DEFAULT ''`；Strategy 存 JSON 字符串。

**理由：** CREATE TABLE IF NOT EXISTS 对已有表不生效，需显式 ALTER；JSON 字符串灵活（字段可选）；零值空串 = 用全局。

## 决策 6：engine 用生效策略替代散开关（e.cfg.*On() → eff.*）

**选择：** Ask/StreamAsk/prepare 的策略判断全部改为 `eff.Query == "multi"`、`eff.Decomposition != "off"`、`eff.Routing == "auto"` 等，基于 `effective(o)` 结果。

**理由：** 生效策略是合并后的唯一事实源，避免散开关与 strategy 两套逻辑并行；`WithStrategy` AskOption 把 kb/请求级策略传入 engine。

## 决策 7：前端仅 KbDetailView 策略区块（ChatView 高级策略可选未做）

**选择：** KbDetailView 加策略设置表单（查询模式/分解/回退/HyDE/路由开关 + 保存调 updateKb）；ChatView 高级策略下拉**未实现**（chat.ts 已支持 req.strategy 字段，前端入口留待后续）。

**理由：** spec 要求前端设置 UI，KbDetailView 是核心入口；ChatView 请求级策略属高级功能，YAGNI 留待按需（API 能力已具备）。

## 配置项汇总

| 配置 | 默认 | 说明 |
|------|------|------|
| `rag.strategy.query` | multi | 查询模式：single/multi |
| `rag.strategy.fusion` | rrf | 多路融合：rrf/none |
| `rag.strategy.decomposition` | off | 问题分解：off/parallel/sequential |
| `rag.strategy.step_back` | off | 回退查询：off/on |
| `rag.strategy.hyde` | off | HyDE 假设文档：off/on |
| `rag.strategy.routing` | off | 自动路由：off/auto |
| knowledge_bases.strategy | 空 | 知识库级策略 JSON（空=全局） |
| 请求体 strategy | 空 | 单次请求策略覆盖 |
