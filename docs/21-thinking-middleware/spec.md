# 思考链路中间件 Spec

## 背景

BinRag 的 RAG 流程包含：**路由判定 → 查询改写（Multi-Query 变体/单查询改写）→ 检索（向量 + BM25 → RRF 融合）→ 重排序 → 上下文组装 → LLM 生成**，复杂问题还会走 **Decomposition 子问题分解 / Step-Back 回退 / HyDE 假设文档** 等策略路径。

但目前这些环节的中间产物——改写后的查询、命中哪些 chunk、rerank 前后排序变化——全部只写入 `slog` 日志，用户只能看到最终 `answer + sources`。用户无法判断"回答依据是否合理、检索是否命中了正确资料"，信任建立困难，问题排查（为什么答错）只能靠开发者翻日志。

## 目标

- G1: 在对话界面提供可折叠的「思考过程」面板，完整展示一次问答的思考链路
- G2: 思考链路**分步流式推送**——每个环节完成后立刻展示，顺序与真实执行一致（思考先行，回答在后）
- G3: 按实际走的路径展示——基础四环节（查询改写、检索、目标 chunks、重排序）+ 策略环节（路由判定、子问题分解、回退查询、HyDE），没走的环节不出现
- G4: 非流式请求同样能拿到完整思考链路（附在响应中）
- G5: 可插拔开关——关闭时行为与现有版本完全一致，零侵入

## 功能需求

- F1: **思考链路事件流**。流式问答新增 `thinking` SSE 事件，每个环节完成后立即推送一段，事件内携带环节类型与结构化数据。事件序列为：`thinking×N → sources → chunk×N → done`（thinking 在 sources 之前全部发完）。
- F2: **路由判定展示**。Routing 开启时展示：判定结果（复杂度、推荐策略、推理说明）。判定失败或未开启时该环节不出现。
- F3: **查询改写展示**。展示改写前后的查询文本：
  - Multi-Query: 生成的全部查询变体（含原问题）；
  - 单查询改写: 原问题 → 改写后查询；
  - 改写失败降级: 说明"使用原问题"。
- F4: **检索过程展示**。展示实际执行的每次检索：查询文本、检索方式（向量 / BM25 / 多路融合 / HyDE 路）、召回 chunk 数。多路检索（Multi-Query、子问题分解）逐路展示。
- F5: **重排序展示**。Reranker 启用时展示：rerank 前后排序对比（chunk 标识 + 前后分数/名次）。Reranker 未启用或失败降级时该环节不出现。
- F6: **目标 chunks 展示**。展示最终进入上下文的 chunk 列表：来源文档、chunk 内容预览（截断，可展开）、最终排序与分数。
- F7: **策略环节展示**。按实际路径展示策略环节：
  - Decomposition: 判定结果、子问题列表、每个子问题的检索结果、综合生成说明；
  - Step-Back: 回退问题、回退检索结果；
  - HyDE: 假设文档内容（预览）、双路检索结果；
  - 策略不适用/失败降级时对应环节不出现。
- F8: **非流式响应附带思考链路**。`/api/v1/chat`（JSON 模式）的响应 `data` 增加 `thinking` 字段，内容与流式一致（一次性完整链路）。
- F9: **开关控制**。通过配置（全局/知识库/请求三级覆盖，复用现有策略体系）控制思考链路是否启用。关闭时：不产生任何 thinking 数据、不影响现有行为与性能。

## 非功能需求

- N1: **主链路不阻塞**。思考链路采集不引入额外网络/IO 等待，失败不影响问答主流程（采集器异常只告警）。
- N2: **关闭零开销**。开关关闭时，除一个 nil 判断外无额外分配与调用。
- N3: **内容截断保护**。chunk 内容、假设文档等长文本默认截断展示（如 200 字符），可展开查看完整内容；总量受控，防止思考事件过大。
- N4: **思考内容不持久化**。thinking 不写入对话历史（历史仍只存 answer + sources），与 DeepSeek 等企业级做法一致。
- N5: **敏感信息**。展示的 chunk 内容与现有 sources 同源，不额外暴露系统信息（prompt、内部配置、堆栈等）。
- N6: **兼容性**。流式事件序列对现有前端保持向后兼容（新增事件，不改变既有事件语义）；非流式响应新增字段不破坏现有字段。
- N7: **并发安全**。多路并行检索（Multi-Query、子问题并行分解）产生的思考数据按路正确归属、顺序稳定。

## 不做的事

- **不持久化思考链路**: thinking 数据不写入数据库、不提供历史查询接口、刷新页面后不保留（仅当轮流式展示）。
- **不做企业级 trace 后端**: 不实现 OpenTelemetry/Langfuse 集成、不做 span 树持久化与检索查询——那是未来的方案 B，本期只做终端用户可见的实时展示。
- **不做思考过程的流式逐步生成**: thinking 推送的是"环节完成后的结果"，不是 LLM 思考 token 的逐字流（那是模型 reasoning 能力，非本系统职责）。
- **不做中间件与引擎解耦的重构**: 不把 RAG 引擎拆成独立可插拔管线（本期在现有引擎内嵌采集点，不做大规模重构）。
- **不做权限/可见性控制**: 思考链路对所有能调用问答接口的客户端可见，不做按用户的精细化权限。
- **不做思考链路的 LLM 摘要/润色**: 展示原始结构化数据，不做二次生成摘要。

## 验收标准

- AC1（F1）: 开启后，流式请求的 SSE 事件流中出现 `thinking` 事件，且全部位于 `sources` 之前；每个 `thinking` 事件含环节类型与结构化数据。
- AC2（F1/F8）: 同一问题分别用流式与非流式请求，两者思考链路内容一致（流式分步、非流式一次返回）。
- AC3（F2）: Routing 开启且判定成功时，thinking 含复杂度、策略、推理说明。
- AC4（F3）: Multi-Query 路径下 thinking 含全部查询变体；单查询改写路径下含改写前后文本。
- AC5（F4）: 多路检索（Multi-Query）时逐路展示召回数，合计与最终融合结果一致。
- AC6（F5）: Reranker 启用时，thinking 含 rerank 前后排序对比；Reranker 关闭时该环节不出现。
- AC7（F6）: 目标 chunks 展示与最终 `sources` 一致（同 chunk 集合，含来源文档与内容预览）。
- AC8（F7）: Decomposition 路径下展示子问题及逐子问题检索结果；Step-Back 路径下展示回退问题；HyDE 路径下展示假设文档；未走的策略不出现。
- AC9（F9/N1/N2）: 关闭后：行为与现有版本完全一致（无 thinking 事件、响应无 thinking 字段），主链路功能与性能不变。
- AC10（N3/N4）: 长文本截断展示；刷新后（或历史接口）不出现 thinking 数据。
- AC11（N7）: 多路并行检索时，thinking 中各路数据归属正确、顺序稳定（多次请求结果结构一致）。
