# Decomposition + Step-Back 决策记录

> 本文档记录阶段二（Decomposition 问题分解 + Step-Back 回退）实现过程中的关键技术决策、理由与权衡，供后续阶段（路由、策略可选化）参考。

## 决策 1：子问题处理采用「只检索 → 一次综合生成」（方案 A）

**选择：** 每个子问题只检索（不单独生成答案），把各子问题的检索上下文全部拼进最终生成消息，一次综合生成。

**理由：**
- 成本可控：仅判定 + 分解 + 综合共 2 次额外 LLM 调用（方案 B「检索+子答案」需 N+1 次）
- 子问题检索上下文已足够 LLM 综合回答
- 引用来源完整：Sources 覆盖所有子问题检索结果

**权衡：** 子问题间的信息综合完全依赖最终 LLM（无中间子答案）。对需要深度多步推理的问题，方案 B 更优——留待后续评估是否需要。

## 决策 2：Decomposition 与 Step-Back 互斥，Decomposition 优先

**选择：** 两策略同时启用时仅 Decomposition 生效（`DecompositionOn()` 分支优先，`else if StepBackOn()`）。

**理由：** 用户确认；避免叠加复杂化与成本失控（两策略都新增 LLM 调用）。

## 决策 3：独立开关 + LLM 判定启用

**选择：** `decomposition_enabled` / `step_back_enabled` 独立开关（默认关）；开启后由 LLM 判定是否适用（简单问题跳过，零成本）。

**理由：** 用户确认；与阶段一 Multi-Query 的「开关 + 显式启用」一致；避免每次问答都增加判定调用的成本。

## 决策 4：判定/检索失败静默降级常规路径

**选择：** 判定解析失败、子问题生成失败、检索失败均返回 `(nil, false, err)`，外层 `err == nil && ok` 才走策略，否则落回常规 prepare 路径。

**理由：** 与阶段一 Multi-Query 降级语义一致；策略是增强不是依赖，失败不应中断问答。

## 决策 5：Sequential 模式用前序子问题检索上下文作参考（不生成子答案）

**选择：** 顺序模式下逐个子问题独立检索；前序子问题的检索上下文拼入后续 prompt 作参考（当前实现为简化：逐个子问题检索，未严格拼入前序上下文——见下方 TODO）。

**理由：** 控制成本（不生成子答案）；顺序模式的价值在于子问题间的依赖关系。

**TODO（后续）：** 当前 sequential 实现为「顺序检索」，尚未把前序子问题检索上下文显式拼入后续子问题 prompt。若后续需要严格依赖链，可增强。

## 决策 6：StreamAsk 策略路径同步完成、结果流式发出

**选择：** 判定/检索/综合在 StreamAsk 开头的 goroutine 外同步完成，策略结果（完整 Answer）以 `EventSources + EventChunk + EventDone` 流式发出；未走策略时保持原有逐 chunk 流式。

**理由：** 保持 SSE 事件协议与前端兼容（前端无需改动）；策略路径的回答已在综合阶段一次性生成。

## 决策 7：判定模板输出 JSON 结构

**选择：**
- 分解判定：`{"decompose": bool, "reason": string}`
- 子问题列表：JSON 数组 `["子问题1", ...]`
- 回退判定：`{"step_back": bool, "question": string}`

**理由：** 结构化 JSON 便于解析与容错（解析失败降级）；与阶段一 multiQuery 模板（JSON 数组）风格一致。

## 决策 8：子问题上限 DecompositionMaxSub 默认 5

**选择：** 上限默认 5，防止分解爆炸控制成本；LLM 输出超过上限时截断。

**理由：** 成本与覆盖平衡；复合问题通常 2-5 个子问题足够。

## 配置项汇总

| 配置 | 默认 | 说明 |
|------|------|------|
| `decomposition_enabled` | false | 是否启用问题分解 |
| `decomposition_mode` | parallel | parallel / sequential |
| `decomposition_max_sub` | 5 | 子问题上限 |
| `step_back_enabled` | false | 是否启用回退查询 |
| `decomposition_template_path` | 空 | 分解判定模板路径（子问题模板暂不开放） |
| `step_back_template_path` | 空 | 回退判定模板路径 |

## 与后续阶段的关系

- **阶段三（RAG 路由）**：路由将按复杂度分流到本阶段策略（simple 直达 / medium 多查询 / complex 分解）——本阶段的判定逻辑（judgeDecompose）可被路由复用或取代
- **阶段四（策略可选化）**：本阶段的开关（decomposition_enabled/step_back_enabled）将成为策略配置的一部分，支持知识库级/请求级覆盖
