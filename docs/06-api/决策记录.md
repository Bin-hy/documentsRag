# API 层与知识库管理 决策记录

## **元数据存储选型？**

* A）SQLite（单文件、零部署、纯 Go 驱动）
* B）PostgreSQL（路线图原定方案，需引入驱动 + 建表迁移 + 部署依赖）
* C）内存存储（最简单但重启全丢）

==选定 B（PostgreSQL），原因是：路线图技术栈明确指定 PostgreSQL；元数据（知识库/文档/任务/API Key/对话历史）是企业级系统的核心资产，需要持久化与并发访问能力；docker-compose 补充 postgres:16 服务，开发环境一键启动。驱动选 jackc/pgx/v5（纯 Go、连接池内建、性能好）。==

## **多知识库如何映射到向量存储？**

* A）单 Qdrant collection + payload metadata（kb_id / document_id / chunk_id / content / metadata），检索时按 kb_id filter
* B）每知识库独立 collection（隔离强但管理复杂）

==选定 A（单 collection + payload filter），原因是：当前规模单 collection 足够，Qdrant 原生 payload 过滤在向量搜索时同步生效；改动最小（pipeline 入库补 kb_id/document_id/chunk_id 字段）。后续规模扩大再评估拆分 collection 或按 tenant 隔离。同时 BM25 索引记录 chunk 所属 kb（Add 带 kbID + SearchFiltered），保证混合检索不串库。==

## **文档上传后的入库处理方式？**

* A）同步入库（上传接口阻塞等待处理完成）
* B）goroutine pool 异步 + 任务状态（上传只保存文件、建任务记录、返回 task_id；后台 worker 执行 Load→Chunk→Embed→Store）
* C）Asynq 消息队列（Redis 调度）

==选定 B（goroutine pool 异步 + 任务状态），原因是：大文档同步处理会长时间占用 HTTP 连接；任务状态持久化到 Postgres（pending/processing/completed/failed + retry_count + error_message），服务重启不丢任务；worker 用 `UPDATE...RETURNING` 原子领取防多 worker 抢同一任务；启动时 processing→pending 防悬挂。后续规模扩大再把任务调度层替换为 Asynq，业务处理逻辑不变。==

## **API 认证怎么做？**

* A）无认证（仅内网/开发）
* B）静态 API Key（`Authorization: Bearer <key>`，SHA-256 hash 存库，支持创建/列表/删除/停用/最后使用时间）
* C）JWT 用户体系（用户表 + token 签发）

==选定 B（静态 API Key），原因是：企业内系统 API Key 足够隔离；只存 hash 不存明文，泄漏面小；预留与知识库绑定的扩展位（后续可限制 key 只访问指定 kb_id）。未来演进多用户 SaaS 再升级 JWT + RBAC。首次启动用配置 bootstrap_api_key 种子（表空时），日志不打印明文。==

## **Web 框架？**

* A）Gin
* B）Fiber

==选定 A（Gin），原因是：路线图技术栈已定，生态最成熟（中间件、SSE、multipart 支持完善），团队熟悉度高。==

## **任务失败如何处理？**

* A）失败即终态，人工干预
* B）自动重试（未超上限回 pending 带退避）+ 手动重试接口（failed→pending 清零次数）

==选定 B，原因是：瞬时错误（网络抖动、服务重启）自动重试即可恢复；永久错误（坏文件）超上限后 failed 且 error_message 可查，通过 `POST /tasks/:id/retry` 手动重试。单文档失败不影响其他任务（错误隔离）。==

## **文档删除如何追溯？**

* A）删除时扫描向量库找该文档的 chunk
* B）文档记录保存 chunk_ids，删除时批量 Delete/Remove

==选定 B，原因是：入库成功后文档表回填 chunk_ids（text[]），删除时直接向量库 Delete + BM25 Remove + 磁盘文件清理 + 记录删除，无需扫描、可追溯。==

## **上传接口的 kb_id 传递方式与大小限制？**

* A）kb_id 放 multipart form 字段，MaxBytesReader 设于读取之后
* B）kb_id 走 query 参数，MaxBytesReader 置于一切 body 读取之前 + uuid 格式校验

==选定 B，原因是：MaxBytesReader 必须在 body 读取前设置，否则大小限制失效（安全审查发现的阻断问题）；kb_id 走 query 不参与 body 解析，超限时能返回明确提示「文件超过大小限制」；uuid.Parse 校验防路径穿越（纵深防御）。==

## **SSE 流式如何实现？**

* A）在 API 层重新定义事件协议
* B）复用 rag.StreamEvent 事件模型（sources→chunk×N→done/error），Gin SSEvent 编码

==选定 B，原因是：阶段六已定义完整的流式事件语义，API 层只需编码透传，避免语义重复。触发方式：`?stream=1` 或 `Accept: text/event-stream`。==

## **统一响应格式？**

* A）裸数据 + HTTP 状态码
* B）`{code, message, data}`（业务码与 HTTP 状态码一致）

==选定 B，原因是：前后端约定清晰，错误信息可携带（如「文件超过大小限制（10MB）」），code=0 表示成功。==

## 技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 元数据存储 | PostgreSQL + pgx/v5 | 路线图原定，纯 Go 驱动，docker-compose 一键启动 |
| 多库隔离 | 单 collection + payload filter（kb_id/document_id/chunk_id） | 改动最小，Qdrant 原生过滤 |
| BM25 多库 | Add 带 kbID + SearchFiltered | 混合检索不串库 |
| 异步入库 | goroutine pool + DB 状态机 | 轻量、状态持久化；后续换 Asynq 不改业务 |
| 任务领取 | UPDATE...RETURNING 原子领取 | 防多 worker 抢任务 |
| 重启恢复 | 启动 processing→pending | 防悬挂任务 |
| 任务处理 ctx | context.WithoutCancel（不受 Shutdown 取消） | 关停时状态能落库，不残留 processing |
| 认证 | 静态 API Key + SHA-256 hash | 简单可管理；预留 kb 绑定 |
| 首启种子 | config bootstrap_api_key（日志不打印明文） | 免手工插库 |
| 上传限制 | MaxBytesReader 先于 body 读取 + uuid 校验 | 防大小限制失效与路径穿越 |
| 文档删除 | 文档表存 chunk_ids 追溯 | 无需扫描向量库 |
| 文件存储 | 本地磁盘（kb_id 子目录） | 简单；后续可换对象存储 |
| SSE | 复用 rag.StreamEvent + Gin SSEvent | 事件语义复用 |
| 统一响应 | {code, message, data} | 前后端约定清晰 |
| Web 框架 | Gin | 路线图已定，生态成熟 |
| Swagger | 本阶段不做 | spec 未覆盖，后续按需引入 swaggo |
