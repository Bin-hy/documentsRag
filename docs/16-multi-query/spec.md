# Multi-Query 多查询 + RAG-Fusion 融合 Spec

## 背景

BinRag 当前问答链路为「单查询改写 → 单路检索（向量+BM25+RRF）→ 重排序 → 生成」。单查询只代表用户问题的一个表达角度，召回率受限——同一问题换一种说法可能命中不同的相关片段。

`docs/15-rag优化计划.md` 阶段一（P0）：引入 **Multi-Query 多查询**（LLM 生成多个查询变体并行检索）与 **RAG-Fusion**（多路结果 RRF 融合），提升召回率与排序质量。

## 目标

- 一个问题生成多个查询变体（多视角表达），并行检索提升召回
- 多路检索结果用 RRF 融合排序（跨查询重复命中的文档靠前），取 Top-K 后走现有重排序
- 多查询作为**可选策略**：启用时替代现有单查询改写（互斥），可配置关闭（回到单查询基线）

## 功能需求

- F1: 多查询生成——启用多查询时，由 LLM 基于原问题（结合对话历史消解指代）生成 N 个查询变体，输出为结构化数组（N 可配置，默认 3）
- F2: 多路检索——原文（或改写后的主查询）与 N 个变体构成 N+1 路查询，并行执行检索，每路返回各自的检索结果
- F3: RAG-Fusion 融合——N+1 路检索结果按 RRF（倒数排序融合）合并排序，跨查询重复命中的文档获得更高累计分数，取 Top-K
- F4: 与单查询互斥——多查询启用时替代单查询改写（不再产生单一改写查询）；关闭多查询时行为与现状完全一致（单查询改写 + 单路检索）
- F5: 配置开关——`multi_query_enabled`（默认关或开由实现定）与 `multi_query_count`（变体数，默认 3）可配置；不改变现有 `enable_rewrite` 语义
- F6: 重排序兼容——融合后的 Top-K 结果继续走现有重排序与上下文组装，引用来源（Sources）与回答流程不受影响

## 非功能需求

- N1: 降级——LLM 生成变体失败（超时/解析错）时降级为单查询（原问题），不中断问答
- N2: 性能——多路检索并行执行（并发上限可配置，默认 3-4 路并发），避免 N+1 倍串行延迟
- N3: 兼容——未启用多查询时零行为变化（回归安全）；检索结果结构与现有下游（重排/上下文/SSE）完全一致
- N4: 可观测——日志记录多查询生成（变体列表）与融合结果（路数/去重后数量），供评估对比

## 不做的事

- 不做 HyDE / Step-Back / Decomposition / 路由（分属阶段二~四，本阶段仅 Multi-Query + RAG-Fusion）
- 不做「先改写再扩展变体」的两级生成（成本高，已决策多查询替代单查询改写）
- 不做变体数量自适应（固定 N，后续阶段按路由复杂度调整）
- 不做多路融合的加权调参（RRF 用统一权重，默认与现有 RRF 一致）

## 验收标准

- AC1: 启用多查询后，问答日志显示生成 N 个变体并并行检索（验证：日志含变体列表与「多路检索」记录）
- AC2: 多路结果 RRF 融合后 Top-K 正确、无重复文档 ID（验证：单测断言融合结果去重且排序）
- AC3: 关闭多查询时行为与现状一致（单查询改写 + 单路检索）（验证：现有测试不回归 + 日志对比）
- AC4: LLM 生成变体失败时降级为单查询，问答正常返回（验证：mock LLM 抛错，观察降级路径）
- AC5: 融合结果继续走重排序与上下文组装，引用来源正常（验证：集成测试，sources 非空且来自融合结果）
- AC6: `multi_query_enabled=false` 时零行为变化（验证：关闭配置跑现有 eval 基线对比）
- AC7: `go build ./...`、`go test ./...`、`go vet ./...` 全部通过
