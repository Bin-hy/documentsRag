# 扫描版 PDF 与无效内容识别拒绝 Spec

## 背景

BinRag 支持多格式文档入库，其中 PDF 解析器基于 pdfcpu 抽取文本。但**扫描版 PDF（每页为图片）**无法抽取可读文字——`ExtractContent` 返回的是 PDF 内部的图像绘制指令（如 `q 595.44 0 0 841.68 cm 1 g /Im10 Do Q`）。这些指令被当作普通段落分块入库，产生两类问题：

1. **检索污染**：乱码 chunk 被向量化后参与检索，命中后 LLM 无法从中提取答案，回答「未找到相关资料。」却显示引用（实测复现：地下空间知识库 5 条引用全是图像指令）
2. **存储浪费**：无效内容占用 Qdrant 向量与磁盘空间

本阶段为入库链路增加**无效内容识别与拒绝**：检测无可读文本的文档（扫描件/空文件/纯乱码），拒绝建库并明确告知用户原因。

## 目标

- 扫描版 PDF 与无可读文本的文档在入库时被识别并**拒绝建库**（任务失败，不写入向量/索引）
- 用户能在前端看到明确失败原因（「扫描件/无可读文本，不支持解析」）
- 上传阶段即可预检提示，避免无效内容进入存储

## 功能需求

- F1: 可读文本判定——解析完成后，若文档可读文本量低于阈值（每页平均或全文），判定为「无可读文本」，拒绝入库
- F2: 拒绝语义——被拒绝的文档入库任务状态为失败，错误信息明确说明「扫描件/图片型文档无可读文本，不支持解析」；不写入向量库、不写入 BM25 索引
- F3: 上传预检——上传接口在保存文件前对 PDF 做快速预检（抽取文本量），若判定扫描件，直接返回明确错误（400 业务码），不创建入库任务
- F4: 任务状态透出——入库任务失败原因可查询，前端任务/文档列表展示失败原因
- F5: 其他格式一致性——所有解析器（TXT/Markdown/PDF/DOCX/CSV/Excel/HTML）统一应用可读文本判定：解析结果为空的文档同样拒绝（空文件、纯乱码）

## 非功能需求

- N1: 阈值可配置——可读文本阈值（最小总字符数与最小平均每页字符数）通过配置项控制，默认值合理（如全文 ≥ 20 字符）
- N2: 性能——预检与入库判定为轻量计算（文本长度统计），不引入额外依赖、不显著增加解析耗时
- N3: 不破坏正常文档——文本型 PDF/DOCX 等正常文档不受影响，判定仅针对「无可读文本」的极端情况
- N4: 兼容性——已入库的历史无效数据不受影响（本阶段只拦截新入库；历史清理不在范围）

## 不做的事

- **不做 OCR**——扫描件图片内容的真实文字识别不在本阶段（成本高、需外部依赖），仅识别并拒绝
- 不清理已入库的历史乱码数据（留待后续管理功能）
- 不改变正常文档的解析/分块/入库行为
- 不新增配置项以外的接口或 UI（前端仅复用现有失败原因展示）

## 验收标准

- AC1: 上传扫描版 PDF 返回明确错误（如「扫描件/无可读文本」），不创建入库任务（验证：上传该 PDF，观察响应与任务列表）
- AC2: 若扫描 PDF 已通过（如预检宽松），入库任务最终为 failed 且 error_message 含「无可读文本」（验证：构造场景观察任务状态）
- AC3: 正常文本 PDF 可正常入库，任务 completed（验证：上传文本 PDF，观察任务成功）
- AC4: 空 TXT / 纯乱码文件入库失败并给出原因（验证：上传空/乱码文件）
- AC5: 被拒绝文档不写入 Qdrant 与 BM25（验证：拒绝后检索不到该文档内容；向量点数量不增）
- AC6: 前端任务列表显示失败原因（验证：浏览器任务/文档列表可见原因）
- AC7: 阈值可配置生效（验证：修改配置阈值后行为相应变化）
- AC8: `go build ./...`、`go test ./...`、`go vet ./...` 全部通过
