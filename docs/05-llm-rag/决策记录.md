# LLM 集成与 RAG 编排

## **LLM 提供者需要支持哪些？**

* A）多 provider 抽象（openai / doubao 各自实现，provider 字段分发）
* B）统一 OpenAI 兼容接口（BaseURL + Model 切换后端）

==推荐 B（已确认），原因是：OpenAI 是事实标准；豆包/DeepSeek/vLLM 均提供 OpenAI 兼容端点（/v1/chat/completions），与现有 Embedder/Reranker 的配置方式完全统一，只需实现一套 HTTP 调用逻辑。多 provider 抽象在本阶段只有两家后端，属于过度设计。==

## **LLM 接口需要哪些能力？**

* A）仅普通生成（输入 messages，输出完整文本）
* B）普通生成 + 流式生成（增量片段返回，便于打字机效果与 SSE 透传）

==推荐 B，原因是：流式是 RAG 问答的必备体验，且阶段七 API 层可直接透传。接口为 `Generate` + `StreamGenerate`，配合函数式 `ChatOption`（WithModel / WithTemperature / WithMaxTokens）按需覆盖配置默认值。==

## **流式响应实现到哪一层？**

* A）客户端层流式（LLM 返回增量片段通道）
* B）本阶段直接做 HTTP SSE 传输

==推荐 A（已确认），原因是：HTTP SSE 是 API 层职责，留到阶段七。客户端层流式保证 LLM 能力就绪，阶段七只需包一层 SSE 编码，避免本阶段引入 HTTP 路由。==

## **流式生成的重试策略？**

* A）任何阶段失败都重试
* B）收到首个 delta 前失败可重试；收到 delta 后失败透传错误，不重试

==推荐 B，原因是：已输出部分内容后重试会产生重复片段，透传错误让调用方决定处理；连接建立阶段的失败（网络错误/5xx/429）与普通生成一致走指数退避重试。==

## **LLM 错误处理策略？**

* A）所有错误直接返回
* B）网络错误 / 5xx / 429 指数退避重试，4xx 直接失败；无 APIKey 时省略鉴权头

==推荐 B，原因是：与 Embedder / Reranker 的重试模式完全一致；无 APIKey 时省略 Authorization 头以支持本地模型（Ollama / vLLM）零鉴权部署。==

## **Query 改写如何接入？**

* A）改写结果同时用于检索和生成
* B）改写仅用于检索，生成仍用原始问题
* C）本阶段不做改写

==推荐 B（已确认），原因是：改写是为了让问题自包含、便于检索；生成阶段用原问题可避免改写引入的语义漂移。改写失败降级用原问题（告警日志），不阻断主链路。改写调用固定低温（0.1）保证输出确定性（改写是「一句话」任务，非创造性生成）。==

## **RAG 编排器的包结构？**

* A）单包 internal/rag（LLM 客户端也放进去）
* B）internal/llm + internal/rag 两包
* C）三包（额外拆分 internal/prompt）

==推荐 B（已确认），原因是：llm 只负责「聊」，阶段七 API 层可独立复用；prompt 模板只被 rag 使用，独立成包违背 YAGNI。==

## **上下文组装（Context Assembly）策略？**

* A）全部检索结果都注入
* B）token 预算截断 + 片段数量上限

==推荐 B，原因是：LLM 上下文窗口有限，超预算会被截断或报错。按 token 预算（默认 2048）+ max_chunks（默认 5）双维度截断；token 用内置轻量估算（中文字符 2 token、英文按词 1 token），零依赖、与 chunker 估算思路一致。==

## **Prompt 模板管理方式？**

* A）硬编码在代码里
* B）内置默认模板 + 配置文件路径覆盖 + text/template 渲染

==推荐 B，原因是：开箱即用（内置中文默认模板：系统提示词、上下文注入、改写提示）；需要定制时通过 config 指向模板文件即可，渲染失败降级默认模板。text/template 为标准库，零额外依赖。==

## **对话历史如何管理？**

* A）仅内存实现，不做抽象
* B）HistoryStore 接口 + 内存实现
* C）本阶段就接数据库（PostgreSQL）

==推荐 B（已确认），原因是：接口抽象让阶段七接入 PostgreSQL 时无需改调用方；内存实现（map + RWMutex）线程安全；容量上限丢最旧（默认 50 条），注入生成请求的条数可配（默认 10 条）。数据库持久化留到阶段七统一做。==

## **引用来源如何标注？**

* A）只返回回答文本
* B）回答 + 结构化引用来源（来源文件名、标题上下文、检索分数）

==推荐 B，原因是：企业知识库问答必须可追溯。系统提示词中要求 LLM 按 [编号] 引用上下文条目，同时 RAGResult 携带结构化 Sources（从检索结果 metadata 提取 filename / heading_context）供调用方渲染引用。==

## **检索结果为空时如何降级？**

* A）报错返回
* B）返回「未找到相关资料」兜底回答，不调用 LLM

==推荐 B，原因是：空结果也是合法用户场景（知识库确实没有答案），明确告知用户优于报错；同时省掉一次 LLM 生成调用。对话历史照常记录，保持多轮对话连续。==

## **可观测性如何保证？**

* A）不做日志
* B）slog 分阶段耗时日志（改写 / 检索 / 组装 / 生成）+ 关键数据（上下文 token 数、引用数、召回数）

==推荐 B，原因是：RAG 链路各阶段耗时分布是阶段八调优的核心依据，日志先行、后续可接指标。==

## 技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| LLM 协议 | OpenAI 兼容 `/v1/chat/completions` | 与 Embedder/Reranker 统一；豆包/DeepSeek/vLLM 均兼容 |
| 流式协议 | SSE text/event-stream 手动解析 | 标准协议，零第三方依赖 |
| 流式重试 | 首 delta 前可重试，之后透传 | 避免重复输出 |
| 选项模式 | 函数式 ChatOption | 调用方按需覆盖温度/模型/max_tokens |
| 改写用途 | 仅用于检索，生成用原问题 | 防改写语义漂移污染生成 |
| 改写温度 | 固定 0.1 | 改写是确定性任务，低温度减少随机性 |
| token 估算 | rag 内置轻量估算（中文 2/字、英文按词） | 与 chunker 思路一致，避免 rag→chunker 跨包耦合 |
| 模板引擎 | text/template + 内置默认 + 文件覆盖 | 零依赖、可定制 |
| 历史存储 | HistoryStore 接口 + 内存 RWMutex | 线程安全、可替换；数据库留阶段七 |
| 溢出防护 | 历史按条数 + 上下文按 token 双维度 | 防上下文溢出 |
| 事件顺序 | Sources 先发 → 文本增量 → Done | 调用方可先拿到引用再渲染正文 |
| 降级 | 检索空→「未找到相关资料」；改写失败→原问题；LLM 失败→上抛 | 保证核心链路可用 |
| 可观测 | slog 分阶段耗时日志 | 便于阶段八评估调优 |
